# 04 · 索引与查询优化

> 索引是图数据库性能的关键。没有索引，按属性查询会退化为全表扫描。

## 1. 为什么需要索引

NebulaGraph 中，**按 VID 查询**（FETCH、GO）不需要索引，因为 VID 直接定位数据。
但**按属性查询**（LOOKUP、MATCH 的 WHERE 条件）需要索引，否则会全表扫描甚至报错。

```sql
-- 没有索引时，这条语句会报错或极慢
LOOKUP ON person WHERE person.age > 28 YIELD person.name;
```

## 2. 索引类型

### 2.1 Tag 索引（点属性索引）

```sql
-- 单属性索引（注意：string 属性必须指定索引长度，如 name(32)）
CREATE TAG INDEX IF NOT EXISTS person_age_index ON person(age);
CREATE TAG INDEX IF NOT EXISTS person_name_index ON person(name(32));

-- 复合索引（多属性，注意顺序）
CREATE TAG INDEX IF NOT EXISTS person_name_age_index ON person(name(32), age);

-- 查看索引
SHOW TAG INDEXES;
DESC TAG INDEX person_age_index;
```

> **string 属性索引必须指定长度**：`name(32)` 表示对 name 的前 32 个字符建索引，
> 最大 256。不指定长度会报 `Invalid param!` 错误。

### 2.2 Edge 索引（边属性索引）

```sql
CREATE EDGE INDEX IF NOT EXISTS work_at_position_index ON work_at(position(32));
SHOW EDGE INDEXES;
```

### 2.3 索引使用规则

| 规则 | 说明 |
|------|------|
| 复合索引前缀匹配 | `(name, age)` 索引支持 `WHERE name == ...`，也支持 `WHERE name == ... AND age > ...`，但不支持单独 `WHERE age > ...` |
| 范围查询 | 支持 `>`, `<`, `>=`, `<=`, `!=` 等 |
| 字符串匹配 | 支持 `==` 精确匹配；模糊匹配（`CONTAINS`）需要全文索引（企业版） |
| 重建索引 | 对**已有数据**建索引后必须 `REBUILD`，否则索引不包含旧数据 |
| 异步生效 | 创建索引后需要等待约 20 秒（2 个心跳周期）才能使用；`REBUILD` 也是异步的，用 `SHOW JOBS` 查看进度 |

### 2.4 重建索引

```sql
-- 对已有数据生效（必须执行！）
REBUILD TAG INDEX person_age_index;
REBUILD EDGE INDEX work_at_position_index;

-- 查看重建任务状态（QUEUE → RUNNING → FINISHED）
SHOW JOBS;
SHOW TAG INDEX STATUS;
```

> **注意**：创建索引后立即 `REBUILD` 可能报 `Index not found`，这是正常的——
> 索引创建是异步的，等待约 20 秒后重新执行即可。

## 3. 查询计划分析

### 3.1 EXPLAIN（查看执行计划）

```sql
EXPLAIN MATCH (v:person) WHERE v.person.age > 28 RETURN v.person.name;
```

输出会显示执行计划，关注：
- 是否使用了索引（`IndexScan` 节点）
- 扫描的数据量（`limit` 等）

### 3.2 PROFILE（查看实际执行统计）

```sql
PROFILE MATCH (v:person) WHERE v.person.age > 28 RETURN v.person.name;
```

输出包含每个算子的实际执行时间、行数，用于定位性能瓶颈。

## 4. 常见优化手段

### 4.1 优先按 VID 查询

能按 VID 定位就按 VID 定位，避免全表扫描：

```sql
-- 快：按 VID
FETCH PROP ON person "p1" YIELD person.name, person.age;

-- 慢：按属性
LOOKUP ON person WHERE person.name == "Alice" YIELD person.name;
```

### 4.2 限制遍历深度和范围

```sql
-- 限制步数
MATCH (v:person)-[:friend*1..2]->(f:person) RETURN f.person.name;

-- 限制返回数量
MATCH (v:person) RETURN v.person.name LIMIT 100;
```

### 4.3 使用 WHERE 下推

在遍历前过滤，减少中间结果：

```sql
-- 推荐：先过滤再遍历（单行）
MATCH (v:person)-[:friend]->(f:person) WHERE v.person.age > 30 RETURN f.person.name;

-- 不推荐：遍历后再过滤（语法上也不支持这种写法）
MATCH (v:person)-[:friend]->(f:person) RETURN f.person.name WHERE v.person.age > 30;
```

### 4.4 避免笛卡尔积

多个 MATCH 子句会产生笛卡尔积，谨慎使用：

```sql
-- 两个独立 MATCH 会做笛卡尔积，数据量大时很慢
MATCH (a:person), (b:company) RETURN a.person.name, b.company.name;

-- 应改为有关联的查询
MATCH (a:person)-[:works_at]->(b:company) RETURN a.person.name, b.company.name;
```

### 4.5 合理设计 VID

- VID 尽量短（FIXED_STRING 长度影响存储和性能）
- 业务上稳定的 ID 作为 VID（如用户 ID、UUID），避免频繁变更
- 避免使用超长字符串作为 VID

## 5. 性能排查流程

1. 用 `EXPLAIN` 看执行计划，确认是否走了索引
2. 用 `PROFILE` 看各算子耗时，定位瓶颈
3. 检查是否缺少索引 → 补索引并 `REBUILD`
4. 检查查询是否产生大量中间结果 → 优化过滤条件
5. 检查遍历深度是否过大 → 限制步数

## 7. 常见问题

| 问题 | 原因与解决 |
|------|-----------|
| `CREATE INDEX ... Invalid param!` | string 属性索引必须指定长度：`name(32)` |
| `REBUILD INDEX ... not found` | 索引创建是异步的，等待约 20 秒后重试 |
| `LOOKUP ... There is no index to use` | 对应属性没有索引，或索引尚未生效 |
| MATCH 返回属性为 NULL | 属性访问必须带 Tag 名：`v.person.name` |
| MATCH 返回空集 | 索引未就绪（REBUILD 未完成），等待后重试 |
| MATCH + LIMIT 间歇性 5 秒 | MATCH 的 LIMIT 下推不稳定（官方已知问题）；不下推时会全量扫描并撞 storage RPC 超时。改用 `LOOKUP ... \| LIMIT` 或 `GO` |

> **关于 MATCH + LIMIT 的性能**：`MATCH ... RETURN ... LIMIT n` 的 LIMIT「下推到存储层」依赖优化器，
> 有时生效（毫秒级）、有时失效（graphd 全量扫描后截断，多分区场景下约 5 秒后才能返回）。
> 同一句 SQL 两次执行耗时可能差 3 个数量级，结果始终正确。需要稳定的 LIMIT 查询时，用：
>
> ```sql
> LOOKUP ON person YIELD person.name, person.age | LIMIT 2;
> ```
