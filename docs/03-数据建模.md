# 03 · 数据建模

> 数据建模是图数据库使用中最重要的一环。建模的好坏直接决定查询的效率和可维护性。

## 1. 图模型三要素

NebulaGraph 的图模型由三要素构成：

| 要素 | 概念 | 类比关系型数据库 |
|------|------|------------------|
| 点（Vertex） | 实体，如一个人、一家公司 | 一行记录 |
| Tag（点类型） | 点的类型定义，描述一类实体的属性 | 一张表 |
| Edge Type（边类型） | 关系的类型定义，描述点与点之间的有向关系 | 一张关联表 |

```
        ┌─────────┐  works_at   ┌──────────────┐
        │ person  │ ──────────▶ │ organization │
        │ (Tag)   │             │    (Tag)     │
        └─────────┘             └──────────────┘
```

## 2. 建模原则

### 2.1 实体 → 点，关系 → 边

- **名词（人、组织、项目、商品、订单）→ 点**
- **动词（任职、购买、关注、属于）→ 边**

### 2.2 属性放哪：点属性 vs 边属性

| 场景 | 放哪 | 示例 |
|------|------|------|
| 实体自身的固有属性 | 点属性 | 人的姓名、年龄 |
| 关系发生时产生的属性 | 边属性 | 任职的职位、入职年份 |
| 会随时间变化的属性 | 边属性 | 订单状态、关注时间 |

### 2.3 一个 Tag 还是多个 Tag？

一个点可以挂多个 Tag（类似多继承）。判断标准：**查询时是否经常一起使用**。

- 经常一起查的属性 → 放同一个 Tag
- 不同业务场景的属性 → 拆成多个 Tag

```sql
-- 示例：一个人同时有 person 和 employee 两个 Tag
CREATE TAG person (name string, age int);
CREATE TAG employee (company string, position string);

-- 插入时同时指定两个 Tag
INSERT VERTEX person (name, age), employee (company, position) VALUES "p1": ("Alice", 30, "NebulaTech", "Engineer");
```

### 2.4 边的方向

边是有向的。建模时确定好方向，查询时保持一致：

```sql
-- 推荐：person -> organization（人指向组织）
INSERT EDGE works_at VALUES "p1" -> "org1": (...);

-- 查询时沿同一方向
MATCH (a:person)-[:works_at]->(o:organization) RETURN ...;
```

## 3. 本体/知识图谱场景建模

结合你的本体项目（onto-builder），本体概念与图模型的映射关系：

| 本体/OWL 概念 | NebulaGraph 图模型 | 说明 |
|---------------|-------------------|------|
| 对象（Object/Class） | Tag | 定义一类实体的属性结构 |
| 关系（Relation/Object Property） | Edge Type | 对象之间的有向关系 |
| 属性（Property/Data Property） | 点/边上的属性字段 | 实体的数据属性 |
| 实例（Individual） | 点（Vertex） | 具体的一条数据 |
| 继承（subClassOf） | 多 Tag 或属性标记 | 用多个 Tag 表达继承关系 |

### 3.1 本体继承的建模方式

本体中常见的继承关系（如"员工"是"人"的子类），有两种建模方式：

**方式一：多 Tag（推荐）**

```sql
CREATE TAG person (name string, age int);
CREATE TAG employee (company string, position string);

-- 员工点同时挂 person + employee 两个 Tag
INSERT VERTEX person (name, age), employee (company, position) VALUES "p1": ("Alice", 30, "NebulaTech", "Engineer");

-- 查所有"人"（含员工）
MATCH (v:person) RETURN v.person.name;
-- 查所有"员工"
MATCH (v:employee) RETURN v.employee.name;
```

**方式二：单 Tag + 类型属性**

```sql
CREATE TAG person (name string, age int, type string);

INSERT VERTEX person (name, age, type) VALUES "p1": ("Alice", 30, "employee");
```

> 方式一查询更灵活（按类型过滤走索引），方式二更简单。数据量大时推荐方式一。

### 3.2 本体关系建模示例

假设本体中有：`人 -[工作于]-> 组织`、`组织 -[拥有]-> 项目`、`人 -[参与]-> 项目`：

```sql
CREATE TAG person (name string);
CREATE TAG organization (name string);
CREATE TAG project (name string);

CREATE EDGE works_at (position string);
CREATE EDGE owns ();
CREATE EDGE works_on (role string);

INSERT VERTEX person (name) VALUES "p1": ("Alice");
INSERT VERTEX organization (name) VALUES "org1": ("NebulaTech");
INSERT VERTEX project (name) VALUES "proj1": ("NebulaGraph");

INSERT EDGE works_at (position) VALUES "p1" -> "org1": ("Engineer");
INSERT EDGE owns () VALUES "org1" -> "proj1": ();
INSERT EDGE works_on (role) VALUES "p1" -> "proj1": ("核心开发");
```

## 4. 建模实战：技术团队知识图谱

完整案例见 [nGQL/05-实战项目.ngql](../nGQL/05-实战项目.ngql)，模型如下：

```
person ──works_at──▶ organization
person ──works_on──▶ project
person ──has_skill──▶ skill
person ──cooperates_with──▶ person
project ──belongs_to──▶ organization
```

**建模决策分析：**

| 决策 | 理由 |
|------|------|
| 技能作为独立点而非 person 属性 | 技能需要被多个 person 共享，且要支持"按技能找人" |
| 协作关系用边而非属性 | 协作是关系，且需要支持多跳遍历 |
| 项目归属组织用边 | 一个项目可能归属多个组织，且要支持"组织-项目-人"多跳查询 |

## 5. 建模检查清单

设计图模型时，问自己：

1. [ ] 每个实体是否都有明确的点类型（Tag）？
2. [ ] 关系是否都建模为边（Edge），而不是塞进属性？
3. [ ] 边方向是否一致且符合查询习惯？
4. [ ] 需要按属性过滤的字段是否计划建索引？
5. [ ] 是否避免了"属性里存列表/JSON 当关系用"的反模式？
